# listing-form-ui Specification

## Purpose
Флоу создания и редактирования заявки: выбор типа, поля по типу, клиентская валидация по общим zod-схемам, публикация нативной `MainButton` Telegram.

## Routes
- `/listings/new` — создание (шаг 1: выбор типа → шаг 2: поля).
- `/listings/:id/edit` — редактирование (сразу шаг 2, тип заблокирован).

## Layout
```
Шаг 1                          Шаг 2 (Почта)                  Шаг 2 (Перевод)
┌─────────────────────┐        ┌─────────────────────┐        ┌───────────────────────────┐
│ Что вы предлагаете? │        │ Тип: Почта          │        │ Тип: Перевод              │
│ ┌─────────────────┐ │        │ Откуда  [_________] │        │ Город, где отдаю деньги   │
│ │ ✉ Почта         │ │        │ Куда    [_________] │        │ [_______________________] │
│ │ Везу посылки    │ │        │ Дата    [📅 ______] │        │ Город, где получат деньги │
│ └─────────────────┘ │        │                     │        │ [_______________________] │
│ ┌─────────────────┐ │        │ Ваш Telegram для    │        │ Сумма, $  [_____]         │
│ │ $ Перевод       │ │        │ связи: @ivan        │        │ Условия/Комиссия [______] │
│ │ Передам деньги  │ │        └─────────────────────┘        │ Ваш Telegram для связи:   │
│ └─────────────────┘ │        [   Опубликовать   ] ← MainButton│ @ivan                   │
└─────────────────────┘                                        └───────────────────────────┘
```
Под каждым полем города — чипсы быстрого выбора (см. «Быстрый выбор города»):
```
Откуда
[ Выберите или введите свой ]
(Балкан) (Ашхабад) (Мары) (Лебап) (Дашогуз) (Казань) (Москва)
```

## Components
| Компонент | Назначение |
|---|---|
| `ListingFormPage` | Контейнер, управляет шагами, MainButton, BackButton |
| `TypePicker` | Две крупные карточки выбора типа |
| `MailFields` | Откуда, Куда, Дата (`<input type="date">` — нативный date picker, `min=today`, `max=today+365`) |
| `TransferFields` | Город отдачи, Город получения, Сумма (`inputmode="decimal"`), Условия/Комиссия (текст, до 200) |
| `CityChips` | Чипсы `POPULAR_CITIES` под каждым полем города: тап подставляет город, отмеченный — `aria-pressed`, город соседнего поля — `disabled` |
| `ContactHint` | «Ваш Telegram для связи: …» (см. `telegram-auth`) |
| `useMainButton(opts)` | Хук-обёртка над `WebApp.MainButton` (text, isVisible, isActive, isProgressVisible, onClick) с очисткой в unmount |
| `useBackButton(onBack)` | Хук-обёртка над `WebApp.BackButton` |

## Form State Machine
```
selectingType → editing ─(submit)→ submitting ─┬─ success → navigate("/my")
                   ↑                            └─ error → editing (ошибки полей / alert)
                   └────────── (Back на шаге 2 при создании) ──────┘
```

## Requirements

### Requirement: Выбор типа
При создании форма SHALL начинаться с выбора типа «Почта» или «Перевод»; на этом шаге `MainButton` скрыта.

#### Scenario: Выбор «Почта»
- **WHEN** пользователь на `/listings/new` нажимает «Почта»
- **THEN** отображаются поля «Откуда», «Куда», «Дата»; `MainButton` видна с текстом «Опубликовать»

#### Scenario: Выбор «Перевод»
- **WHEN** пользователь нажимает «Перевод»
- **THEN** отображаются поля «Город, где отдаю деньги», «Город, где получат деньги», «Сумма, $», «Условия/Комиссия»

#### Scenario: Смена типа на шаге 2
- **WHEN** пользователь на шаге 2 нажимает Telegram `BackButton`
- **THEN** возвращается на шаг выбора типа; введённые данные сбрасываются

### Requirement: Валидация на клиенте
Форма SHALL валидировать поля теми же zod-схемами из `packages/shared`, что и сервер. Ошибки поля показываются после первого blur поля или после попытки отправки, цветом `--tg-theme-destructive-text-color`.

#### Scenario: Невалидная форма
- **WHEN** обязательные поля пусты
- **THEN** `MainButton` видна, но неактивна (`MainButton.disable()`, цвет `--tg-theme-hint-color`)

#### Scenario: Валидная форма
- **WHEN** все обязательные поля заполнены корректно
- **THEN** `MainButton.enable()`

#### Scenario: Дата в прошлом
- **WHEN** пользователь вводит дату раньше сегодняшней (например, вручную на desktop-клиенте)
- **THEN** под полем «Дата вылета не может быть в прошлом», `MainButton` неактивна

#### Scenario: Сумма с запятой
- **WHEN** пользователь вводит «1500,5»
- **THEN** значение нормализуется в `1500.5` и считается валидным

### Requirement: Публикация через MainButton
Отправка формы SHALL выполняться только нативной `WebApp.MainButton` с текстом «Опубликовать» (создание) или «Сохранить» (редактирование). Во время запроса MUST показываться прогресс и блокироваться повторная отправка.

#### Scenario: Успешная публикация
- **WHEN** пользователь нажимает «Опубликовать» на валидной форме
- **THEN** вызывается `MainButton.showProgress()`, отправляется `POST /api/listings`
- **AND** после `201`: `HapticFeedback.notificationOccurred("success")`, `MainButton.hideProgress()`, переход на `/my`, новая заявка первой в списке, кэши ленты и «Моих заявок» инвалидированы

#### Scenario: Двойное нажатие
- **WHEN** пользователь нажимает `MainButton` дважды во время запроса
- **THEN** отправляется ровно один запрос

#### Scenario: Ошибка валидации с сервера
- **WHEN** сервер вернул `400 VALIDATION_ERROR` с `details`
- **THEN** ошибки отображаются под соответствующими полями, `HapticFeedback.notificationOccurred("error")`

#### Scenario: Прочая ошибка сервера
- **WHEN** сервер вернул `409`, `429` или `5xx`
- **THEN** `WebApp.showAlert(error.message)`, данные формы сохранены, `MainButton` снова активна

#### Scenario: Уход с формы
- **WHEN** пользователь покидает форму (успех или Back)
- **THEN** `MainButton` скрывается и обработчики `onClick` снимаются

### Requirement: Редактирование
На `/listings/:id/edit` форма SHALL быть предзаполнена данными заявки; тип отображается как неизменяемый; отправка — `PATCH /api/listings/:id` только изменённых полей.

#### Scenario: Предзаполнение
- **WHEN** открыта форма редактирования MAIL-заявки
- **THEN** поля содержат текущие значения, шаг выбора типа пропущен, `MainButton` = «Сохранить»

#### Scenario: Нет изменений
- **WHEN** пользователь ничего не изменил
- **THEN** `MainButton` неактивна

#### Scenario: Сохранение
- **WHEN** пользователь изменил «Куда» и нажал «Сохранить»
- **THEN** отправляется `PATCH` с телом `{ toCity: "..." }`, после `200` — переход на `/my`

#### Scenario: Заявка не найдена или чужая
- **WHEN** `GET /api/listings/:id` вернул `404` или заявка имеет `isOwn = false`
- **THEN** показывается «Заявка не найдена» и кнопка «К моим заявкам»

### Requirement: Навигация назад
На экранах формы SHALL показываться `WebApp.BackButton`; нижняя панель вкладок скрыта.

#### Scenario: Back на шаге выбора типа или в редактировании
- **WHEN** пользователь нажимает `BackButton`
- **THEN** возврат на `/my`, `BackButton` скрыта

#### Scenario: Back с несохранёнными изменениями
- **WHEN** в форме есть введённые данные и пользователь уходит с формы на `/my`
- **THEN** `WebApp.showConfirm("Отменить изменения?")`; при отмене пользователь остаётся на форме

### Requirement: Быстрый выбор города
Под каждым полем города формы (оба типа, создание и редактирование) SHALL показываться чипсы популярных городов `POPULAR_CITIES` из `packages/shared` в порядке: Балкан, Ашхабад, Мары, Лебап, Дашогуз, Казань, Москва. Тап по чипсу подставляет город в поле; свободный ввод своего города MUST оставаться доступным. Группа чипсов имеет `aria-label` «Быстрый выбор: <подпись поля>».

#### Scenario: Чипсы в форме
- **WHEN** пользователь выбрал тип «Почта» или «Перевод»
- **THEN** под обоими полями городов отображаются 7 чипсов в заданном порядке

#### Scenario: Выбор из списка
- **WHEN** пользователь нажимает чипс «Мары» под полем «Откуда»
- **THEN** поле «Откуда» содержит «Мары», чипс отмечен (`aria-pressed="true"`), вызывается `HapticFeedback.selectionChanged()`

#### Scenario: Свой город
- **WHEN** пользователь вписывает в «Откуда» «Стамбул», заполняет остальные поля и нажимает «Опубликовать»
- **THEN** ни один чипс под «Откуда» не отмечен
- **AND** `POST /api/listings` отправляется с `fromCity: "Стамбул"`

#### Scenario: Отметка без учёта регистра
- **WHEN** поле «Откуда» содержит « ашхабад »
- **THEN** отмечен чипс «Ашхабад» (сравнение через `normalizeCity`)

#### Scenario: Город соседнего поля
- **WHEN** поле «Откуда» содержит «Ашхабад»
- **THEN** чипс «Ашхабад» под полем «Куда» неактивен (`disabled`)

#### Scenario: Выбор города при редактировании
- **WHEN** в форме редактирования MAIL-заявки пользователь нажимает чипс «Казань» под «Куда» и «Сохранить»
- **THEN** отправляется `PATCH` с телом `{ toCity: "Казань" }`

### Requirement: Поле «Комментарий»
Форма обоих типов SHALL содержать последним необязательное поле «Комментарий» — многострочное (`<textarea>`, до 300 символов) с placeholder «Можете указать способ связи». Пустое поле не мешает публикации.

#### Scenario: Поле в форме
- **WHEN** пользователь выбрал тип «Почта» или «Перевод»
- **THEN** последним полем формы отображается «Комментарий» с placeholder «Можете указать способ связи»

#### Scenario: Публикация с комментарием
- **WHEN** пользователь заполнил обязательные поля и «Комментарий» = «WhatsApp +99365000000» и нажал «Опубликовать»
- **THEN** `POST /api/listings` содержит `comment: "WhatsApp +99365000000"`

#### Scenario: Публикация без комментария
- **WHEN** «Комментарий» пуст
- **THEN** `MainButton` активна на валидной форме, в теле `POST` нет поля `comment`

#### Scenario: Очистка при редактировании
- **WHEN** в форме редактирования заявки с комментарием пользователь очищает «Комментарий» и нажимает «Сохранить»
- **THEN** отправляется `PATCH` с телом `{ comment: null }`
